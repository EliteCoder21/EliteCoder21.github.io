The [CSE 484 binary lab](https://courses.cs.washington.edu/courses/cse484/26au/assignments/cse484-binlab_handout.html) pushed me to look at programs from an unfamiliar angle. Instead of asking only what the author intended a program to do, I had to ask what the running process would actually do with unexpected input.

The lab's deliberately vulnerable C programs made concepts like buffers, stack frames, and control flow much more concrete. A local array is not an isolated box: it lives next to other information in a process's memory. If a program writes beyond its bounds, the consequences depend on what sits nearby and how the program later uses it. Seeing that relationship made memory safety feel much less like a rule to memorize.

## Following the program, not my assumptions

I spent time connecting source code to the state of a running program in a debugger. I had to think about where data lived, how a function returned, and what assumptions about a memory layout were actually supported by the build I was looking at. It was tempting to treat an address or an offset as a universal fact. The more useful habit was to inspect the process and understand why it had that value in that environment.

The format-string exercises gave me another way to think about trust boundaries. A string supplied as data can have a very different meaning when a program treats it as a formatting instruction. That small-looking change in how an API is called can let input influence behavior the author never intended.

The later targets also encouraged me to trace the effects of corrupted data beyond the original write, including how memory-management metadata and saved control information are used. What interested me most was the chain of cause and effect: an operation can look ordinary in isolation, but its assumptions become dangerous when earlier data has been corrupted.

## What I am taking with me

I don't see the exercise as a collection of tricks to memorize. It taught me to slow down, examine what a program trusts, and distinguish a hypothesis from what I have actually observed. Addresses, compiler choices, and runtime details matter; an explanation that works for one build is not automatically proof for another.

That perspective has stayed with me beyond the lab. When I write or review code now, I think more carefully about where input comes from, whether a boundary is enforced, and what else depends on the integrity of the data I am handling.
